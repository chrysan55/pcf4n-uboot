# ADR 0007: FPGA-first configuration with QSPI-only SPL payload loading

- Status: Accepted for bring-up
- Date: 2026-08-31

## Context

PCF4N must bring the FPGA fabric to user mode before starting the HPS so the
fabric can operate independently and UART1 can expose the HPS boot sequence.
The SDM-side Macronix QSPI stores both the full FPGA configuration and the HPS
second-stage `u-boot.itb`.

Initial UART logs proved that HPS release, UART1, PLL setup, both DDR IO96B
calibrations, and ECC initialization all succeed. One FPGA image reported
8 GiB while the QSPI-ownership-enabled image reports 4 GiB, so usable capacity
must be confirmed from the final Quartus handoff instead of either provisional
log.
The failing SPL instead printed `Trying to boot from RAM` and returned
`-EINVAL`. That path cannot load the QSPI payload: it means the device tree in
the running SPL allowed a `/memory` fallback after storage probes failed.

After Quartus QSPI ownership was changed to HPS, SPL reported a 400 MHz QSPI
reference clock, selected SPI, and verified the CRC of the FIT configuration,
BL31, U-Boot proper, and its FDT. The remaining reset is therefore after FIT
verification, at the SMMU/SDM/FDT/BL31 handoff boundary. The running banner is
still the unmarked `2026.01-g6e59447316d0` build, not the current PCF4N
diagnostic build.

The locked TF-A source defaults `SOCFPGA_UART_CONFIG` to zero, which sends all
BL31 boot/crash output to UART0. PCF4N reserves UART0 for the MCU data channel
and observes bring-up on UART1, so the previous BL31 failure interval was
invisible even when TF-A was running.

The UART1 diagnostic build subsequently proved every SPL handoff step and BL31
initialization completes. BL31 prepares a normal-world EL2h entry at
`0x80200000` with SPSR `0x3c9`, then no U-Boot proper banner appears. The fault
boundary is therefore the ERET/BL33 earliest-entry interval, not QSPI, FIT,
SMMU, the SDM stage notification, or BL31 runtime-service initialization.
BL31's printed `Argument #0 = 0x1` is not by itself a failure: this U-Boot
board's strong `save_boot_params` implementation branches directly back to
`save_boot_params_ret` and does not consume `x0` through `x3`.

The next capture produced the complete `ABCDEF[f0][fdt][cpu][dm][serial>]`
sequence. This proves normal-world DDR execution, UART1 access, SError
unmasking, the initial stack, appended FDT, CPU setup, and driver-model setup.
With pre-console buffering and silent-console support disabled,
`console_init_f()` has no blocking operation; the remaining failure is inside
`serial_init()` while selecting or probing the UART1 NS16550 device. The board
override now states the handoff-observed 100 MHz L4 SP/UART clock explicitly,
and the next diagnostic traces DT translation, clock selection, reset
deassertion, and the transmitter-empty wait.

## Mode semantics and reset ownership

FPGA-configuration-first is a configuration and boot-order selection, not a
statement that a separately powered FPGA starts and later supplies power to the
HPS. After device POR the SDM configures the FPGA I/O and fabric, configures the
HPS EMIF I/O, copies the FSBL into HPS OCRAM, and then releases the HPS from
reset. The HPS is held in reset while the fabric is configured.

This mode does not transfer ownership of HPS internal resets to FPGA soft
logic. The HPS Reset Manager still controls CPU, peripheral, and bridge reset
registers. After the SDM releases the HPS reset domains, software releases the
peripherals it needs. FPGA logic can participate in warm-reset handshakes,
observe HPS reset outputs, and reset its own application logic, but those paths
do not replace `PER0MODRST`, `PER1MODRST`, or `BRGMODRST` management.

Reset lookup/deassertion errors are therefore not an expected consequence of
FPGA-first mode. They indicate a handoff/DT mismatch, an unavailable clock or
reset domain, incorrect bridge wiring or sequencing, or a bootloader driver
problem. In particular, the current timer2 `-ENOENT` is generated by a
diagnostic-only deletion of its `resets` property, while the UART1 reset skip is
also a diagnostic workaround. Neither is a required FPGA-first setting.

## Decision

- Use FPGA-configuration-first mode. Embed `u-boot-spl-dtb.hex` in the full
  FPGA `.sof`, select Quartus `HPS_INITIALIZATION = After INIT_DONE`, and omit
  the PFG `hps=on` option. In a saved PFG XML, `hps="1"` is the HPS-first
  selection and must not be present in the FPGA-first output definition.
- Assign QSPI ownership to HPS in Quartus. SPL requests direct ownership from
  the SDM mailbox before probing the Cadence QSPI controller.
- Build the JIC from the complete, final `.sof`; FPGA-first does not use the
  HPS-first peripheral/baseline plus core-RBF phase split.
- Require free-running HPS and HPS-EMIF reference clocks at the frequencies
  recorded in the Quartus project. Keep an external pull-up on
  `HPS_COLD_nRESET` and ensure no FPGA/CPLD output contends with the pin when
  the SDM changes it from output-low to input during HPS release.
- Instantiate Reset Release IP and keep FPGA application logic reset until the
  entire fabric is in user mode. If the application logic additionally waits
  for HPS readiness, use the documented `h2f_gp_out[1]` release contract and
  do not drive it high before the relevant logic is ready.
- When HPS-FPGA bridges are used, connect their documented reset inputs to
  `h2f_reset`, keep traffic quiescent during bridge reset, and implement the
  warm-reset handshake where required. Leave unused bridges in reset.
- Retain the normal HPS Reset Manager nodes and reset specifiers in the SPL,
  U-Boot, and Linux device trees. Remove diagnostic reset bypasses after the
  current timer/MMC failure is isolated.
- Load `u-boot.itb` only from the agreed QSPI offset; do not fall back to a
  preloaded RAM image.
- Disable the Simics-only target inherited from Altera's base defconfig.
- Enable detailed SPL boot errors during bring-up.
- Print the SDM mailbox direct-mode return code and SPI-NOR probe return code.
  Until the first complete boot succeeds, use single-line 25 MHz HPS-side
  reads; this does not change the SDM's AS x4 FPGA-configuration mode.
- Build bring-up TF-A with `SOCFPGA_UART_CONFIG=1`, `DEBUG=1`, and
  `LOG_LEVEL=50`, and rebuild it from an isolated clean object directory so
  UART0 objects cannot be reused accidentally.
- Print checkpoints after FIT loading, SMMU setup, the SDM SSBL notification,
  FIT FDT fixup, and immediately before entering BL31. Enable SPL FIT printing
  so the loaded addresses are visible in the same UART capture.
- In the current diagnostic iteration, print the BL33 entry words, both Agilex
  5 DDR firewall DMI register sets (`0x18000800` and `0x18000a00`), UART1
  firewall state, and EL2 registers in BL31 immediately before ERET. Emit raw
  UART1 markers from U-Boot proper before stack setup, immediately before/after
  SError unmasking, and around early FDT/driver-model/serial initialization.
- Identify every programmed HEX by banner timestamp and SHA-256, and preserve
  the final PFG map with the JIC.

## Consequences

- A missing QSPI grant, unrecognized flash, or invalid flash node now fails at
  the QSPI selection/probe stage instead of being disguised as a RAM-image
  parse failure.
- The FPGA can reach user mode before HPS software starts.
- During bring-up, BL31 debug/runtime/crash output is visible on UART1. This is
  a diagnostic setting and must be removed together with the UART1 console
  before that port is handed to the MCU upgrade protocol.
- The JIC remains a cross-team artifact: the HPS repository supplies SPL and
  ITB, while the logic team supplies the matching `.sof`, ownership setting,
  partition map, and final Quartus output.
- Production release remains blocked until the `u-boot.itb` offset and maximum
  partition length are confirmed from the final PFG map.

## BL33 entry diagnostic interpretation

The BL33-entry package expected and observed
`1400000a d503201f 000b90b8 58000dd0` at `0x80200000`. The UART1-probe capture
then matched `1400000a d503201f 000b9240 58000dd0`, and the successful
UART1-reset-preserve capture matched
`1400000a d503201f 000b92d0 58000dd0`, and the timer2 package expected
`1400000a d503201f 000b92c0 58000dd0`. The architecture-timer control package
expected `1400000a d503201f 000b8c18 58000dd0`; the timer/MMC boundary package
expected `1400000a d503201f 000b9890 58000dd0`. Treat each four-word sequence as
an exact package signature; a mismatch means BL31 is not seeing the U-Boot
payload packaged in that FIT.

| Last output | Boundary isolated |
| --- | --- |
| BL31 preflight is absent | The diagnostic BL31 is stale, or BL31 stops before its platform runtime hook |
| Correct preflight, but no `A` | EL3-to-EL2 ERET/non-secure DDR fetch, or the first non-secure UART1 access; use the printed UART1 firewall value to distinguish them |
| `A` only | Branch to, write within, or return from `save_boot_params` |
| `AB` only | EL detection and VBAR/HCR/CPTR setup |
| `ABC` only | Pending SError is taken by `msr daifclr, #0x4` |
| `ABCD` only | Counter-frequency setup or its following ISB |
| `ABCDE` only | CPU erratum or low-level initialization |
| `ABCDEF` only | `_main` stack/global-data setup before `board_init_f` |
| `[f0]` but no `[fdt]` | Monitor-length or appended-FDT setup |
| `[fdt]` but no `[cpu]` | Event/trace or `arch_cpu_init` stage |
| `[cpu]` but no `[dm]` | Machine CPU or driver-model initialization |
| `[dm]` but no `[serial>]` | Remaining pre-console board initialization |
| `[serial>]` but no `[console]` | Driver-model serial initialization |
| `[console]` but no U-Boot banner | Display/checkcpu or later `board_init_f` initialization |

Within the UART1-probe build, the expected sub-sequence is `[of>]` (the
NS16550 driver's DT conversion begins), `[addr]`, `[clk=05f5e100]` (100 MHz),
`[probe>]`, `[rst=00000000]`, `[temt=........]`, `[temt<]`, `[probe<]`, and
`[serial<]`. The first missing marker identifies the exact failing operation;
in particular, `[temt=...]` without `[temt<]` proves the indefinite wait for
UART LSR bit 6.

The UART1-probe capture stopped at `[probe>]`, after DT address and 100 MHz
clock resolution but before the combined reset result marker. Therefore the
remaining operation is reset acquisition/deassertion. Because SPL and BL31
already initialized UART1 and the BL33 raw markers prove it is live in EL2,
the current build preserves UART1's reset state only in U-Boot proper and
prints `[rst-skip]`. SPL still performs the original reset operation. A
successful continuation should be `[rst-skip][temt=........][temt<][probe<]`
`[serial<][console]`, followed by the normal U-Boot banner.

That continuation is now observed twice, before and after relocation. U-Boot
proper prints its banner, CPU/model/DRAM information, and the driver-model
summary, then stops during `MMC:` with `Could not initialize timer (err -19)`.
The message originates in `dm_timer_init()` and `-19` is `ENODEV`: it is not an
eMMC-controller failure. The base defconfig enables both the timer uclass and
the DesignWare APB timer driver, but the PCF4N board DTS had inherited all four
APB timer nodes as disabled.

Unlike the Stratix 10 SPL path, the Agilex 5 SPL path does not clear
PER1MODRST bit 4 before calling `timer_init()`: its `timer_s10.c`
implementation initializes the ARM architected counter instead. Therefore
`L4SYSTIMER0_RESET`, which belongs to `timer2@10d00000`, can still be asserted
when U-Boot proper starts. Enabling timer2 while deleting its reset property
cannot preserve a state that SPL never established.

The resulting timer2 capture reaches the driver's reset lookup and prints
`Can't get reset: -2`. This is the driver's warning for the deliberately
absent `resets` property (`-ENOENT`) and is not a fatal return. It proves only
that the device was bound and `dw_apb_timer_probe()` reached reset acquisition;
it does not prove that clock lookup, register programming, the uclass
post-probe hook, or the first counter read completed.

An ARMv8 architected-counter variant is useful as a control because SPL and
BL31 already use that counter, but it bypasses the APB timer and cannot by
itself identify the failing component. It also cannot repair a later Cadence
SD6HC PHY, controller, clock, reset, or eMMC electrical failure.

The exact caller provides a stronger hypothesis. During `MMC:`, the Cadence
probe requests and deasserts reset IDs 6, 15, and 7 (COMBOPHY, SDMMC OCP, and
SDMMC). SoCFPGA reset deassertion clears each reset bit and calls a 500 ms
`wait_for_bit_le32()`; its first `get_timer()` call starts timer2 and produces
the observed warning. Replacing timer2 can make this wait expire, but the
upstream Cadence probe ignores the return value of `reset_deassert_bulk()` and
then accesses the controller. If a reset remains asserted, the later MMIO may
still block. This reset-failure path is currently the leading hypothesis, not
yet a confirmed root cause.

The timer2 diagnostic kept `CONFIG_TIMER=y`, kept
`CONFIG_DESIGNWARE_APB_TIMER=y`, and selected timer2. It marked clock lookup,
each timer MMIO operation, and two counter reads separated by an architected
10 us delay. After a moving counter is established, it brackets MMC DT parsing,
Cadence PHY reset/register setup, `sdhci_setup_cfg()`, and `sdhci_probe()`.
Interpret the final marker as follows:

| Final completed marker | Isolated boundary |
| --- | --- |
| `[rst:id=N,before=...>]` | reset N clear/write/wait has begun; N=6/15/7 maps to COMBOPHY/SDMMC OCP/SDMMC |
| `[rst:id=N,ret=-110,...]` | reset N failed to clear within 500 ms; this confirms the reset path rather than the timer warning as the first functional failure |
| `[tmr:clk>]` | timer clock lookup/rate access |
| `[tmr:load>]`, `[tmr:curr>]`, or `[tmr:ctrl>]` | the following APB timer register access |
| `[tmr:stalled]` | timer registers respond but the counter does not advance |
| `[tmr:ok]` followed by an MMC/PHY marker | timer probe completed; use that later marker to locate the Cadence stage |
| `[phy:rst-off>]` without a result | PHY-init-complete polling; a working timer should turn this into a 3 ms timeout rather than a silent infinite wait |
| `[mmc:cdns<]` | Cadence controller probe completed; investigate later card initialization/commands |

The board capture completed every timer MMIO marker but reported
`[tmr:count=00000000>00000000][tmr:stalled]` twice, followed by
`Could not initialize timer (err -110)`. This confirms that APB transactions
reach timer2 while its counter remains held reset; it is not an SD6HC PHY
calibration result. Restoring timer2's reset property alone is unsafe because
the generic SoCFPGA reset driver's `wait_for_bit_le32()` calls `get_timer()`
before checking the reset bit, recursively probing the timer that is trying to
deassert its own reset.

The next diagnostic therefore removes `/chosen/tick-timer`, leaves the APB
timers at their inherited disabled state, and sets `CONFIG_TIMER=n` as well as
`CONFIG_DESIGNWARE_APB_TIMER=n`. On ARM64 this makes the legacy U-Boot timing
API use the mandatory architected `CNTPCT_EL0` counter and `CNTFRQ_EL0` rate.
This is not expected to repair an MMC reset, PHY, or electrical fault; it
removes the broken timebase so the existing reset and Cadence markers can
identify that later fault accurately.

The resulting `pcf4n-arch-timer-mmc-diag` HEX/ITB pair was validated on the
board on 2026-08-31 and reaches the U-Boot proper command prompt. This confirms
that the fatal initialization failure was the DM/APB timer dependency rather
than the proposed 4-bit PHY default table. Full eMMC enumeration and repeated
4-bit I/O remain separate board-validation gates.

## Rejected explicit PHY-default override

The proposed 4-bit timing table matches the locked U-Boot 2026.01 Cadence
SD6HC defaults exactly. The driver selects these tables by timing mode rather
than `bus-width`, and the locked Linux driver does not consume the raw U-Boot
properties. Adding the table to the board DTS would therefore create no PHY
register change, so the override was not retained; validation continues with
the `pcf4n-arch-timer-mmc-diag` artifact pair.
